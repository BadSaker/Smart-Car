# 队友 Git 同步使用说明

双击项目根目录的 [项目同步.cmd](../项目同步.cmd)。脚本使用 Git for Windows 和系统 Windows PowerShell 5.1，不需要 Python、管理员权限或额外 PowerShell 模块；执行策略只在启动的进程内生效。

## 首次接手

1. 安装 Git for Windows，保留 Git Credential Manager，重新打开终端；接受仓库协作者邀请。
2. 在准备放置项目的目录打开终端，克隆到一个新目录（不能用 GitHub 的 Download ZIP 代替）：

   ```powershell
   git clone https://github.com/BadSaker/Smart-Car.git
   ```

   HTTPS 认证按 Git Credential Manager 提示登录自己的 GitHub 账号。现有 SSH 克隆也支持，但需自行配置 SSH 密钥。不要复制队友的 `.git` 或共用凭据。详见 [GitHub 认证说明](https://docs.github.com/en/get-started/git-basics/caching-your-github-credentials-in-git)。
3. 双击 `项目同步.cmd`，选择 **3 本地配置**，填写自己的姓名与邮箱并确认。邮箱可填写 GitHub 关联邮箱，或从 GitHub Settings → Emails 复制隐私邮箱。配置仅写当前仓库；作者身份与 GitHub 登录是两回事。
4. 参照 [本地环境](local-environment.md) 配置热点、Keil 和仿真工具。它们不会随 Git 自动安装。

旧目录还有进展时保留旧目录，先比较后迁移源码；不要把旧目录整包覆盖到新克隆中。首次克隆会下载历史，之后一般只传新增对象；Git 不会同步被忽略的工具链、Python 环境和缓存。

## 菜单

| 选项 | 行为 |
| --- | --- |
| 1 查看本地状态 | 不联网，显示修改、缓存的分支状态、保留分支与 stash 恢复点 |
| 2 提交并上传我的修改 | 先 fetch；展示文件清单/差异统计，可选看完整差异；输入提交说明、确认提交；再确认上传本地 main 的全部未上传提交 |
| 3 本地配置 | 查看有效姓名邮箱，输入新配置，仅保存当前仓库 |
| 4 仅保存本地提交 | 先尝试 fetch；输入提交说明并确认保存，不上传。fetch 失败时可明确确认离线保存 |
| 5 更新至云端版本 | 先 fetch；展示影响，输入 `UPDATE`；保存恢复分支及必要的 stash，再把本地 main 对齐到本次获取的 origin/main |
| 6 获取云端最新记录（Fetch） | 仅获取 origin/main 最新记录并显示状态；不改变本地分支、文件或未提交修改 |

2、4、5 仅支持 `main`。Git 操作未完成、有锁、存在子模块、稀疏检出或隐藏工作区修改的索引标志时停止，交由熟悉 Git 的队友处理。菜单不会自动切换分支、合并、强制推送或运行 `git clean`。

**Fetch 只刷新本机记录的云端历史，不改变本地分支、文件和未提交修改。** 只想了解云端进展时选 6，无需先提交本地修改；2、4、5 仍自动执行 fetch。1 显示的云端信息可能过时。2、5、6 的 fetch 失败会报错停止，绝不使用旧缓存覆盖本地。

### 保存和上传

2、4 的提交说明必须自己填写，例如“调整右弯转向参数，降低入弯速度”；空白取消。已有修改先展示清单，可输入 D 查看已跟踪文件的完整差异；新文件需要自行打开检查。输入 Y 后提交**整个仓库所有未忽略的新增、修改和删除**，包括原有暂存内容，不按文件交互选择。

检查不想分享的文件、固件内嵌热点密码和大文件后再确认。不想全部提交时取消，先由熟悉 Git 的队友处理。`.gitignore` 不会自动排除已经被跟踪的文件。

没有修改时不会创建空提交；2 仍可上传以前保存的本地提交。上传失败或取消上传后，本地提交保留；可以再次选择 2 重试，无需重复提交。提交失败时文件/暂存内容保留，按 Git 错误处理。

如果双方有新提交，推送通常会被拒绝：需要保留自己的进展时，请找队友或 Codex 合并，**不要为了上传而选 5**。普通上传绝不强推。origin 存在多个地址或下载/上传地址不一致时停止上传，避免误传。

### 更新到云端（放弃当前代码状态）

5 用于“我想直接使用云端这版”。这可能前进，也可能回退；它不合并本地工作，不改变 GitHub 上的提交。

执行前保存并关闭编辑器，停止其他 Git 操作和会改写项目文件的程序。脚本显示将覆盖的提交、修改、新文件及版本差异；输入大写 `UPDATE` 后：

1. 创建本地 `backup/sync-时间-随机编号` 分支，保留原 HEAD 的提交历史。
2. 如有未提交内容，用 `git stash push --include-untracked` 保存受跟踪修改、暂存区及未跟踪文件，显示 stash 提交编号。
3. 保存成功、工作区清理完成且忽略内容无冲突后，才将 main 重置为刚获取的云端提交。

恢复点只在本机，不自动推送，也不是整包压缩备份；不要随意删除恢复分支、drop/clear stash 或删除 `.git`。存储失败、空间不足等异常会停止；操作不是跨多条 Git 命令的事务，中途失败时可能已经创建恢复点、把修改移入 stash，按屏幕提示恢复，不要反复清理。忽略文件不会被备份。

本地热点、工具路径和缓存等被忽略文件保留；若云端跟踪路径与它们重名或有文件/目录前缀冲突，脚本停止。嵌套仓库等无法完整保存的内容也可能使操作停止。因此对齐的是 Git 管理的代码，而不是删除整个目录后重建。

## 找回更新前的进展

先选 1 查看恢复分支和 stash，再让 Codex 或熟悉 Git 的队友帮助恢复。恢复前先保存当前新进展，不能直接叠加覆盖。典型恢复操作如下，**占位值必须替换成菜单显示的真实编号**：

```powershell
git switch backup/sync-实际编号
# 仅当此次更新确实创建了 stash 时执行；使用记录的提交哈希，避免选错其他 stash。
git stash apply --index 实际stash提交哈希
```

保留分支包含原来的已提交进展；stash 包含当时的未提交/未跟踪进展，`--index` 同时尝试恢复暂存状态。不要自动删除 stash；核对恢复内容后再决定。恢复后的分支不是 main，菜单写操作会拒绝，需进一步决定合并或切回 main。

## 团队约定与验证

日常先看本地状态；无须保留本地进展、希望完全采用云端时选 5；开发中选 4；完成验证后选 2。多人同时改同一文件前先沟通。自动获取云端记录不代表已把云端代码合入本地。

实现：[project-sync.ps1](../car/scripts/project-sync.ps1)。回归测试仅在 `tmp/project-sync-tests-*` 建立临时远端及两份克隆，结束后删除本次临时目录，不连接 GitHub：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File car/tests/test_project_sync.ps1
```

脚本不编译、烧录或验证实车。GitHub 登录、网络可达性和远端权限需在每位队友电脑上首次操作时确认。
