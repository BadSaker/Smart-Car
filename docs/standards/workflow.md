# 审核、执行与交付流程

## 开始任务

每次用户提出新指令，先复述目标、现状理解、计划、涉及路径、预期产物及验证方法，等待用户明确审核同意后执行。需要硬件信息时列出缺失项及其影响，不能把推荐型号当作确认结果。

2026-09-30的项目初始化、文档建立和 `car/` 工程移植属于已完成的历史授权，不作为新任务许可。审核针对具体计划与范围，计划内授权跨步骤持续有效，不逐条命令重复询问。用户补充信息可用于推进同一计划；新增功能、修改原始资料、扩大清理范围或其他越界变更需要先复述新的范围并重新审核。

开工先读 [AGENTS.md](../../AGENTS.md)、[项目概况](../project-overview.md)、最近日志和受影响文档。确认已经完成的工作，避免重复执行或把旧问题当成新问题。

工作目录应为包含 `AGENTS.md` 和 `car/autocar.uvprojx` 的项目根目录。`CLAUDE.md`只导入共享规则，不复制正文。接手回复明确列出本次保护范围；[结构检查脚本](../../car/scripts/check_project_layout.ps1)检查文件、工程引用和共享源码位置，不证明规则已被阅读，也不执行构建或硬件操作。

## 执行与记录

1. 明确当前事实、未确认假设和风险对应的验证方法。
2. 在允许目录执行最小必要改动，保留来源与版本；临时材料进入本任务 `tmp/` 子目录。
3. 执行命令前说明目的与工作路径，完成后检查退出码及结果。
4. 对改动进行合适验证，出现失败先记录证据并查明原因，再修改；不要用未运行测试支持成功结论。
5. 同步长期文档与每日日志，记录剩余问题及下一步的条件。

持续工作中及时说明已知结果、尚存不确定项以及接下来的验证。不可将一次编译通过表述为硬件功能或赛道成绩通过。

## 日志要求

使用 `logs/YYYY-MM-DD.log`，时间按 Asia/Shanghai，追加记录而非覆盖已有内容。单次构建/测试的过程日志由脚本写入 `car/build/`（不提交），不作为 `logs/` 下的独立文件长期留存。每条记录至少包含：

```text
[2026-09-30 15:30:00 +08:00] 任务：项目初始化
范围：涉及的目录或文件
变更：具体改动及依据
验证：命令、退出码、关键结果；未运行项明确注明
产物：最终文件位置
未解决：阻塞、待确认事实与继续条件
```

## 交付与收尾

- 固件放入 `outputs/firmware/`，报告放入 `outputs/reports/`；默认以 git 提交作为变更留痕，不再逐次生成整包备份，确需存档时才放入 `outputs/backups/`。
- 核对文档链接和工程引用；报告说明工具版本、来源版本、测试范围和限制。
- 删除本任务临时目录，按 [commands.md](commands.md) 检查绝对路径，保留空 `tmp/`。
- 最终回复说明完成了什么、如何验证、最终产物在哪、什么尚未确认。需要进一步审核时展示具体可审查结果和扩大范围的理由。

实物型号、接线、舵机中位、PWM 极性、编码器方向、电池配置或赛道测试未核实时，应写入 [hardware-and-pins.md](../hardware-and-pins.md) 或 [known-issues.md](../known-issues.md)，不能通过省略说明把它们视为已解决。
