# src 代码精简与可读性分析

日期：2026-10-28。范围：`car/src/` 的 15 个 C 文件、相关接口、构建引用、测试与仿真入口，以及 GitHub 上的智能车源码。此次交付为分析方案，未实施重构。

建议先在原文件内整理视觉和自动驾驶流程，提取确实同义的计算，再考虑分文件。现有代码已经具备通用 PID、左右侧参数化和硬件适配边界，不需要整体换成开源项目的架构。可维护性收益主要来自减少同一处需要同时理解的状态和分支；严格保留功能时，没有证据支持将总代码量削减一半。

## 建议的精简方案

### 优先做原文件内的职责整理

**1. 将视觉入口整理成清楚的阶段。** 在 `track_vision.c` 内先提取 `static` 函数，让入口呈现“初始化与输入检查 → 原始扫描及证据 → 元素判断 → 外侧重扫 → 路径构造 → 轮迹核验 → 结果收尾”。这是阅读层面的分段，实际调用顺序保持现在的顺序，尤其保留最后基于几何结果的入环确认与出口确认。

建议先提取轮迹扫描块（1549–1598 附近）、轮廓结果合入块和几何结果发布块；再拆 `vision_contour_path` 中的轮廓采样、局部圆/直线模型拟合、中心路径及目标生成。工作数组 `xs/ys/sums/cnt` 继续使用静态存储，不能顺手变成大尺寸栈变量。原文件明确约束 8 KB 主栈，视觉接口也不支持重入。

**收益：** 入口可明显缩短，便于检查每一步输入输出；总行数可能增加。先不拆成多个 C 文件，可避免一次改动波及工程清单和仿真构建。

**2. 将自动驾驶 tick 按职责分段。** 对 `autonomous_drive_tick`（174–312）提取具名函数，例如运行保护、转向请求、速度上限、双轮目标、PID 与输出跟踪。展开多语句同行，解释 `d/i` 在长函数中的含义；可以在内部使用更直观的形参名，不必改变公共接口。

这一步必须保持以下顺序：

- 路径诊断与新帧计数保持原位置；停车键先于启动处理。
- 新鲜度、元素、连续坏帧和超时保护保持当前优先级，多故障同时出现时故障码也应一致。
- 短时坏帧立即撤动力、保留已执行转向；不能共用会回中和清状态的完整 `zero_output`。
- 新帧更新转向请求，每个 10 ms tick 推进转向轨迹和速度闭环。
- 两轮目标分别限斜率，再按当前方式修正平均速度；PID 输出限斜率之后才回算积分。

**收益：** 降低阅读负担，不承诺减少物理行数。第一轮保留 `autonomous_drive_t`、输入和输出结构布局，避免额外影响测试与诊断使用者。

### 可以实际减少重复的局部改动

**3. 合并完全相同的环内进入动作，保留两条进入判据。** `track_vision.c:753` 和 `1631–1632` 都执行清出口记忆、清路径记忆并切到 `ROUNDABOUT_INSIDE`。可提取 `vision_enter_inside(now_ms, distance_mm)`，由两处在原位置调用；后一处对 `out->element` 的更新仍由原调用点负责。

`vision.curve_seen` 在当前生产源码、测试及仿真检索中只见声明和上述两处写入，没有读取，可列为私有无效状态清理项。它不在公开结果结构中。移除它前仍应检查结构整体访问和链接结果；不把所有历史标志一并删除。

**收益：** 少量行数，但避免两条入环路径以后清状态不一致。风险低于合并进入判据。

**4. 提取视觉中的基础计算，保留每次统计的语义。** 可考虑：

- `vision_cross_direction`（555）和 `vision_cross_update_direction`（577）重复的线性回归求斜率与截距，抽取最终求解部分，保留各自样本筛选、累加顺序、最小样本数和方向验收。
- `vision_contour_path`、`vision_metric_pixel_path` 和轮迹核验中的像素/地面投影，抽取表达式一致的计算。当前存在整数 `vision_width(row)` 与浮点宽度两种用法，不能统一成一套取整后宣称等价。
- 左右边线数组、实测位和对侧的选择可用少量具名辅助函数；对 `TRACK_SIDE_NONE` 显式保留原行为。现有 `vision_gap`、`vision_opposite_continuous`、`vision_forward_branch` 已按侧复用，不应重新复制左右实现。
- 对模型种类 0/1/2、拒绝位、故障限界位补具名常量，保持原数值与类型，避免诊断解释漂移。

**收益：** 减少算式和方向选择的重复，数学含义更集中；必须用原始灰度序列做逐帧差分。不要创建一个收纳所有小函数的宽泛 `utils.c`。

**5. 简化台架电机阶段，保留遥控和自动后端。** `motor_control.c:334–433` 的 `REMOTE_CONTROL_ENABLED=0` 分支中，单轮驱动、等待、另一轮驱动、等待、双轮驱动是固定序列。可以先提取“写输出、切状态、清阶段计时”的小函数；如果仍显得重复，再用包含持续时间、输出通道和下一状态的常量表。

保留 `motor_finish` 的结果展示时间、原始停车键优先级和非法状态兜底。不要把模式枚举直接当连续表下标，也不要把遥控与台架两个 tick 机械拼成一个复杂通用引擎。`motor_remote_zero_output`（456–459）只是转调 `motor_zero_output`，可删除这一层静态包装并调整内部调用。

**收益：** 固定阶段的重复可减少；主要改善备用台架分支，对默认遥控配置的固件体积不一定有收益。

**6. 把硬件适配与诊断组装分成具名步骤。** `autonomous_control.c:36–72` 组装视觉摘要，`73–136` 组装输入、调用控制器并维护 trace。建议提取纯粹的字段映射和诊断记录辅助函数，仍在原位置调用。

第一轮保留 mailbox 的值复制、临界区和结构字段，不使用指向主循环结果的指针来省复制，不用宏批量生成映射。`servo_control.c:215` 已有通用执行器入口，只需把 `servo_remote_owned` 及其 1/2 改成含义准确的所有者命名/常量；存储类型及遥控、自动的切换语义保持。

**收益：** 可读性为主，总行数可能小幅增加。

### 旧代码退役需单独决定兼容边界

**7. 区分“不参与当前行驶”与“可删除”。** 当前 `main.c` 使用 `track_vision_process` 和 `binaryzation_process`，速度与转向控制使用 `control_pid_step`。检索未发现运行链调用旧 `pid.c` 的接口，也未发现运行链调用 `get_hist_gram`、`get_threshold_otsu`、`auxiliary_process`。

已有链接 map 进一步支持这一点：`car/build/listings/autocar.map:11719–11747` 将这三个图像函数及旧 PID 的函数、参数和状态列为移除节。这是读取现存构建产物的结果，本轮没有重新链接。

但 `car/tests/test_algorithms.c`、`car/scripts/test.ps1` 仍验证这些旧接口，`car/include/main.h` 仍包含 `pid.h`，MDK 工程也列有 `pid.c`。因此有三种选择：

| 选择 | 对当前功能的影响 | 代码量收益 |
| --- | --- | --- |
| 保留文件及接口，标明旧算法用途 | 最保守，测试和旧接口均保留 | 总量不减，减少误读 |
| 从固件工程排除旧 PID，保留原位置供测试使用 | 当前运行路径不依赖它，需重建确认；旧测试仍可用 | 固件工程更清楚，仓库总量不减 |
| 正式退役旧接口并删除实现、声明及对应旧测试 | 当前驾驶行为可望保持，但旧算法 API 与教学/测试能力发生变化 | 仅相关 C 实现约 270–280 行，约占 src 的 5.2%–5.4%；不是此次严格保留全部功能的默认方案 |

不能承诺删除这些源码会缩小当前 BIN，因为现有 map 已显示相应节被链接器剔除。也不能用旧 PID 替换 `control_pid.c`：两者在积分、采样周期、微分、非法输入和饱和处理上并不等价。

## 不应作为冗余合并的部分

| 看起来相近的代码 | 必须保留的区别 |
| --- | --- |
| `vision_path_quality`、`vision_path_reliability`、`vision_curve_outer_support` | 原始覆盖、当前路径通行支持和普通外侧模式许可是不同职责；其中固定远场与移动预瞄窗口的统计也不完全相同 |
| 第一遍扫描和外侧重扫 | 元素先依据原始证据判定；重扫会清空/重建 `features`，不能跨阶段缓存一次统计供全部消费者使用 |
| 普通候选和暂定十字中的环岛重判 | 普通候选可先积累缺口/分叉，再要求当前岛边；十字重判要求每次计数同时具备岛边。合并条件会改变确认帧数 |
| 提前的 `vision_elements` 与处理末尾的几何入环确认 | 两者读取的路径结果不同。移动到同一位置可能改变同一帧的路径生成和状态 |
| `vision_cache_expire` 与状态内超时处理 | 清理字段及触发阶段并非完全相同，不能仅按“都是超时”删除其中一处 |
| 自动、遥控和台架输出 | 换向零输出间隔、仅变化时写 PWM、台架结果保留和撤权方式不同；通用 setter 容易改变硬件调用次数/顺序 |
| 自动/电机/舵机/Wi-Fi 按键处理 | 有按 tick 累计与按时间戳计时之别，初始化与重新武装也有差异。首轮不引入统一按键框架，Wi-Fi 更属于冻结范围 |
| 两次遥控会话检查、两次舵机状态读取 | 用来捕获阻塞读取期间或硬件写入期间的代次变化，不能只留一次快照 |
| `main.c` 多次 `app_service_controls` | 为不同耗时操作之间提供服务点；合并调用会改变响应和舵机新鲜度 |
| 看似空的 ISR | 仍可能清溢出/中断标志或调用供应商处理；不能按“没有算法”删除 |

`camera_debug.c`、`camera_display.c` 及 main 中相应调用顺序按[冻结约束](../../docs/seekfree-assistant-debugging.md#屏幕与wi-fi冻结约束)保留。`isr.c` 末尾中断名称说明可整理成文档，但这只是注释维护，收益次于核心模块，版权声明必须保留。

## 三种路线与推荐顺序

| 路线 | 内容 | 取舍 |
| --- | --- | --- |
| A 原文件内等价整理，推荐先做 | 展开密集写法、具名阶段函数、同义小计算复用、私有无效状态清理 | 影响面最小；重复减少，但格式化后总行数可能上升 |
| B 在 A 验证后按职责分文件 | 将视觉拆成扫描、几何、元素和入口；必要时拆电机模式 | 单文件更短，净行数通常不降；要处理内部状态归属和多处构建引用 |
| C 同时退役旧接口 | 清除旧 PID 和旧图像算法及其测试入口 | 可再减少约 270–280 行 C 实现，但兼容范围变化，需要用户选择 |

路线 A 中，真正可去重的规模预计为几十至百余行量级，这是基于重复片段的工程估算，未制作补丁测量，不能作为验收承诺。不要以压缩空行、连写语句或合并不同保护条件达成行数指标。

建议把未来实施分成三次可独立验证的改动：先整理自动驾驶 tick 与命名，再整理视觉阶段及同义计算，最后处理电机台架阶段。是否采用路线 B、C，在 A 的实际收益明确后再定。本次用户批准的是分析，不把上述推荐视为实施授权。

## 保持行为不变的验证方案

“功能不变”应包括：公开接口、默认及已支持的编译配置、每帧视觉结果、每拍控制输出、状态切换与故障优先级、遥控解析和撤权、诊断冻结，以及硬件访问的顺序。减少源代码不等于减少周期耗时；板端时间仍需测量。

### 先建立同输入差分

未来实施时，在相同编译器、优化选项、配置下分别构建改前和改后版本，使用相同灰度、帧完成时间、里程、编码器、按键及服务时间序列。基线来自当时工作区的实际内容，不能默认 Git HEAD 包含用户全部改动。基线只能作为任务临时验证快照，不形成第二套长期算法维护位置。

- 视觉逐帧比较所有边线/中线/行标志、阈值、有效性、Q、元素阶段、候选结果、几何目标、拒绝原因和历史诊断。

- 整数、枚举、标志与故障触发拍要求完全一致；浮点先检查相同工具链下的位级差异。出现差异先解释来源，不通过任意扩大误差容限掩盖分支变化。
- 结构比较按字段进行，不对含填充字节的整个 C 结构使用 `memcmp`。外设桩同时记录 GPIO/PWM 的顺序和次数，不能只比较最终占空比。
